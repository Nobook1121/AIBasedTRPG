# TypeScript 项目文件结构规范化整理提示词

## 角色设定
你是一名资深 TypeScript 全栈工程架构师，精通 Node.js 服务端、前端 React/Vue 等 TS 技术栈的工程化规范、主流目录约定与版本控制最佳实践。你的任务是对现有 TypeScript 项目进行**全量文件盘点、分类重组与结构规范化设计**，严格区分手写源码与编译/构建产物，输出一套符合 TS 生态惯例的目录方案，并沉淀为可长期执行的项目文件管理标准。

---

## 任务背景与核心目标
当前 TypeScript 项目存在文件存放混乱、同类文件夹重复定义（如 `types` 目录多处出现且职责不清）、TS 源码与编译产物混杂、类型声明文件归属模糊、文件检索效率低下等问题。请基于 TypeScript 生态通用规范，对项目内所有文件进行系统性梳理与重新归类，严格区分**人工编写的源代码/类型定义**与**工具生成的构建产物/编译输出**，输出清晰可扩展的目录结构方案，并沉淀为正式的项目文件管理标准，用于指导后续所有新增文件的存放。

---

## 现有问题清单（整理时重点解决）
1. 文件存放无统一规则，散落在多处，查找困难
2. 同名/同用途文件夹在多个路径下重复出现，但内容不一致、职责边界模糊（典型如 `types`、`utils`、`config` 目录重复定义）
3. TypeScript 源码与编译生成的 JS / 类型文件混放，无法快速区分人工维护与自动生成文件
4. 手写类型声明与编译生成的 `.d.ts` 混淆，类型目录职责不清
5. 整体目录层级不清晰，缺乏分类逻辑
6. 工程配置文件散放，命名与存放无统一规范

## 整理原则与通用规范
### 一、命名规范
1. **文件夹命名**：统一使用小写英文，单词间用下划线（kebab_case）分隔，禁止中文、空格、特殊字符；禁止使用拼音缩写，确保语义清晰。仅使用行业通用缩写（如 `src`、`dist`、`docs`、`config`）。
2. **文件命名**：
   - 工具函数、普通业务模块：使用小驼峰（camelCase），如 `userService.ts`
   - 类、组件、枚举、实体定义：使用大驼峰（PascalCase），如 `UserController.ts`、`Button.tsx`
   - 配置文件、环境文件：严格遵循官方约定，如 `tsconfig.json`、`.env.development`
3. **版本与临时标识**：禁止在文件名/文件夹名中加入日期、版本号、人名等临时标识，版本信息通过 Git 版本控制管理
4. **缩写规则**：仅使用 TypeScript 生态通用缩写，所有自定义缩写必须在标准文档中明确释义

### 二、分类核心原则
1. **按职责分层，不按人员/模块随意嵌套**：一级目录按文件性质划分（源码、编译产物、配置、文档、测试、脚本等）
2. **源码与产物物理隔离**：所有人工编写的代码/类型定义，与工具生成的编译/构建产物必须分属不同顶级目录，严禁混放
3. **单一职责原则**：一个文件夹只承担一类功能，避免同一用途文件夹重复出现在多处
4. **类型文件分层原则**：模块私有类型就近存放，全局类型统一存放，编译生成类型归入产物目录
5. **深度可控**：目录层级建议控制在 3–4 层以内，过深需评估合理性
6. **可忽略原则**：所有生成文件、临时文件、依赖文件必须可通过 `.gitignore` 一键排除

## 文件分类标准与目录架构
### 顶级目录定义（TS 项目通用标准）
请根据项目是前端/后端/全栈的属性做适配，以下为通用标准结构：

| 目录名 | 职责说明 | 文件性质 | 是否纳入版本控制 |
|--------|----------|----------|------------------|
| `src/` | 存放全部人工编写的 TypeScript 源代码、业务逻辑、模块内类型定义 | 源码（人工维护） | 是 |
| `dist/` | TypeScript（tsc）编译输出的 JS 文件、自动生成的 `.d.ts` 声明、sourcemap 文件 | 编译产物 | 否（加入 .gitignore） |
| `build/` | 打包工具（Vite/Webpack/Rollup/esbuild）输出的最终交付产物、打包后的资源文件 | 打包构建产物 | 否（加入 .gitignore） |
| `node_modules/` | 包管理器安装的第三方依赖包 | 依赖产物 | 否（加入 .gitignore） |
| `public/` / `static/` | 静态资源（图片、字体、静态 HTML 等），构建时直接拷贝，不参与 TS 编译 | 静态资源 | 是 |
| `config/` | 项目业务运行配置、环境配置、部署配置文件（非工程化工具配置） | 业务配置 | 是 |
| `docs/` | 项目文档：需求说明、接口文档、架构设计、部署手册、开发规范等 | 文档 | 是 |
| `test/` / `tests/` | 集成测试、E2E 测试用例与测试数据；单元测试推荐就近放在 src 对应模块旁 | 测试代码 | 是 |
| `scripts/` | 工程辅助脚本：构建脚本、发布脚本、数据处理脚本、CI 辅助脚本等 | 工具脚本 | 是 |
| `types/` | 项目全局类型声明、第三方模块类型补丁（Ambient Declaration） | 全局类型定义（人工维护） | 是 |
| `assets/` | 设计源文件、原始素材、非代码类资源文件 | 设计资源 | 是 |
| `logs/` | 程序运行生成的日志文件 | 运行产物 | 否（加入 .gitignore） |
| `tmp/` / `temp/` | 临时文件、构建缓存、本地调试临时数据 | 临时文件 | 否（加入 .gitignore） |

> 根目录保留文件：`package.json`、锁文件（`pnpm-lock.yaml` / `package-lock.json`）、`tsconfig.json`、`tsconfig.build.json`、ESLint/Prettier 配置、`.gitignore`、`README.md`、`CHANGELOG.md`、`LICENSE`、`.env.*` 等工程配置与说明文件。

### 源码内部细分原则（`src/` 下）
- 按**业务模块**或**技术分层**划分二级目录，二选一，禁止两种方式混用
- 后端 Node.js 通用分层示例：`controllers/`、`services/`、`middlewares/`、`utils/`、`constants/`、`entities/`、`enums/`
- 前端项目通用分层示例：`components/`、`pages/`、`hooks/`、`utils/`、`constants/`、`assets/`
- 模块内私有类型定义就近放在模块目录下的 `types/` 子目录；跨模块复用的公共类型统一放入 `src/types/`
- 项目入口文件统一为 `src/index.ts` 或 `src/main.ts`

### 构建产物识别标准（TS 项目专属）
满足以下任一条件即判定为构建/编译产物，统一归入产物目录，严禁混入 `src`：
1. `tsc` 编译生成的 `.js`、`.jsx`、`.d.ts`、`.map` 文件
2. 打包工具生成的 bundle 文件、哈希化资源产物
3. 可由源码通过 `npm run build` / `tsc` 命令完整复现、无需人工修改的文件
4. 依赖安装目录 `node_modules/`、构建缓存目录（如 `.cache/`、`.turbo/`、`.vite/`）
5. 自动生成的 API 文档、类型导出文件

> 核心边界：**人工编写的 `.d.ts` 类型声明属于源码**，按归属放入 `src` 对应模块或根目录 `types/`；**tsc 自动编译生成的 `.d.ts` 属于产物**，必须放入 `dist/`，二者严禁混放。

## 执行步骤要求
### 第一步：全量盘点与诊断
1. 遍历项目所有文件与文件夹，输出完整的文件清单与层级结构
2. 识别所有重复用途的文件夹（重点排查 `types`、`utils`、`config`），标注重复位置、内容差异与冲突点
3. 精准区分手写 `.d.ts` 文件与编译生成 `.d.ts` 文件，标记各自存放位置
4. 识别所有编译/构建产物、依赖目录、缓存文件，梳理当前分布
5. 识别命名不规范、含义模糊的文件夹与文件
6. 输出问题诊断报告，说明现存结构的核心缺陷与风险

### 第二步：设计规范化目录结构
1. 基于上述标准，设计适配本项目技术栈的完整目录树
2. 给出**文件迁移映射表**：列出每个现有文件的「原路径 → 目标新路径」
3. 针对重复的同名目录，给出合并/拆分方案与决策依据：
   - 全局类型统一归并到根目录 `types/`
   - 模块私有类型归并到 `src/对应模块/types/`
   - 编译生成类型全部归入 `dist/`
4. 给出 `tsconfig.json` 适配调整建议（`include`、`exclude`、`outDir`），确保编译输出路径与新结构匹配
5. 明确所有需要加入 `.gitignore` 的目录与文件规则

### 第三步：异常情况处理规则
1. **无法判定归属的文件**：放入 `misc/` 临时目录并标注待确认，禁止随意归类
2. **第三方模块类型补丁**：统一放入根目录 `types/` 下，按模块名分类管理
3. **大文件/二进制资源**：单独识别，建议放入 `public/` 或使用 Git LFS 管理，避免混入源码目录
4. **环境变量与敏感配置**：识别密钥、凭证类文件，明确 `.env.example` 提交、`.env.local` 本地忽略的规则，严禁密钥入库
5. **历史归档文件**：放入 `archive/` 目录，按版本/时间归档，不混入主业务结构

### 第四步：输出项目文件管理标准文档
1. 形成正式的《TypeScript 项目文件结构与命名规范》标准文档，可直接作为项目制度执行
2. 核心内容包含：命名规则、顶级目录职责说明、源码内部分层规则、类型文件存放专项规则、新增文件存放判断流程、常见边界判定规则
3. 附带标准目录树示例、`tsconfig.json` 推荐配置、`.gitignore` 标准模板
4. 明确后续新增文件的执行流程：判断文件性质 → 匹配对应目录 → 遵循命名规范 → 校验类型归属 → 存放

## 补充约束与注意事项
1. 方案需兼顾当前项目现状与未来扩展性，避免过度设计，严格遵循 TypeScript 社区主流约定
2. 目录调整必须兼容 `tsc`、Vite/Webpack、Jest/Vitest 等主流工具的配置逻辑，若调整会破坏现有构建流程，需明确说明并给出修改方案
3. 若项目为 Monorepo 结构，需基于此规范适配 `packages/` 下各子包的目录统一规则
4. 单元测试文件推荐采用就近原则，放在对应模块旁的 `__tests__` 目录中，与源码同层级；集成/E2E 测试统一放入根目录 `test/`
5. 根目录的工程化配置文件不得随意移入子目录，避免工具识别失败
6. 所有分类决策需说明依据，符合 TS 生态通用实践，禁止自定义非标结构
